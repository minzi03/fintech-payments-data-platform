# GC-PORTAL-002-04 — Login-Intent Contract Amendment

- Decision ID: `GC-PORTAL-002-04`
- Status: **PROPOSED**
- Date: 2026-07-26
- Authority: repository governance authority
- Scope owner: Portal security implementation
- Resolves: GC-PORTAL-002-01 Blocker 4
- Production deployment authorization: **NOT GRANTED**

## 1. Context

GC-PORTAL-002-01 Blocker 4 identified that the frozen design (section 15) defines:

- `GET /v1/auth/login-context` returning a "Short-lived login-intent view";
- `POST /v1/auth/login` requiring "Login-intent + Origin";
- `LoginContextView` as a model.

But does not specify:

- The `LoginContextView` response schema;
- The login-intent token format, storage, or transport;
- Whether a new database table is required;
- The lifetime and expiry behavior;
- What the browser may or may not submit.

ADR-PORTAL-002-07 (frozen) states: "Login starts with same-origin POST plus a short-lived
browser-bound login intent."

This amendment defines the login-intent contract.

The critical governance principle is:

> **Login intent describes the requested post-login action.
> Login intent does not establish identity, role, entitlement, or authorization.**

## 2. Governance decision

### 2.1 Login-intent purpose

The login intent is an anti-CSRF and return-path binding mechanism. It:

- proves that the login request originated from a Portal-initiated flow (anti-CSRF);
- binds the post-login redirect to an allowlisted return path;
- carries no identity, role, tenant, environment, or authorization context;
- is short-lived, single-use, and server-controlled.

### 2.2 Login-intent lifecycle

1. **Creation** — `GET /v1/auth/login-context` generates a login intent on the server.
2. **Distribution** — the intent token is returned to the browser in the JSON response.
3. **Presentation** — `POST /v1/auth/login` includes the intent token in the request body.
4. **Validation** — the server validates the intent before creating the login transaction.
5. **Consumption** — the intent is consumed and cannot be reused.
6. **Destruction** — the intent expires after its bounded lifetime.

### 2.3 GET /v1/auth/login-context

**Authentication:** Not required (pre-authentication endpoint).

**CSRF:** Not required (safe endpoint, no state transition, pre-authentication).

**Response — login-context view:**

| Field | Type | Source | Description |
|---|---|---|---|
| `intent_token` | string | Server-generated | Opaque, high-entropy, single-use token |
| `selected_provider` | string | Server-configured | Default or configured authentication provider |
| `return_to` | string \| null | Server-derived | Allowlisted return path (if any) |
| `expires_at` | ISO 8601 | Server-computed | Intent expiry timestamp |

The response contains only what the server decides. The browser cannot influence the response.

For `return_to`: the server is authoritative. The browser may request a return path, but the
server decides whether it is allowed. The browser cannot bypass the allowlist.

### 2.4 POST /v1/auth/login

**Authentication:** Not required (pre-authentication endpoint).

**CSRF:** Login-intent + Origin (frozen in design freeze section 15).

**Required request body:**

| Field | Type | Source | Description |
|---|---|---|---|
| `intent_token` | string | Browser-submitted | The intent token received from login-context |

**Optional request body:**

| Field | Type | Source | Description |
|---|---|---|---|
| `return_to` | string \| null | Browser-submitted | Requested return path (validated against allowlist) |

**Forbidden request fields:**

The browser MUST NOT submit any of the following. If present, the server MUST ignore or reject:

- `role`, `roles`, `group`, `groups` — identity/authorization context
- `tenant`, `organization` — tenant context
- `environment` — environment selection
- `principal`, `subject`, `user` — identity claims
- `token`, `access_token`, `id_token` — OIDC tokens
- Any field not explicitly listed as required or optional above

The server does not trust browser-supplied identity, authorization, or token fields. This is a
frozen invariant (section 4: "no trusted role, tenant, environment, or authorization context
from browser input").

### 2.5 Intent token format

The intent token is:

- a high-entropy, cryptographically random, opaque string;
- generated by the server;
- stored server-controlled with the associated login-context metadata;
- bound to the session or browser-binding context;
- single-use and short-lived;
- never derived from predictable values.

The token format is an implementation detail. It may be:

- a random bearer token validated against server-side storage;
- or a signed/encrypted server-generated artifact.

Governance requires only that the token is opaque, high-entropy, single-use, and
server-validated.

### 2.6 Server-side intent storage

The login intent is stored server-side with:

| Field | Description |
|---|---|
| Protected intent representation | Server-side representation of the intent token (never the plaintext) |
| Created timestamp | UTC timestamp of creation |
| Expiry timestamp | UTC timestamp of expiry |
| Consumed flag | Whether the intent has been used |
| Selected provider | The authentication provider for this login |
| Validated return path | The validated return path (if any) |
| Browser-binding reference | Reference to the browser-binding context (if applicable) |

The intent does NOT store:

- identity, role, tenant, or environment claims;
- authorization decisions or policy references;
- OIDC tokens or token material.

### 2.7 Intent validation at POST /v1/auth/login

When the browser submits `POST /v1/auth/login`:

1. Validate the `Origin` header (exact match) or `Referer` (fallback).
2. Validate the `intent_token` against server-side storage:
   - token exists;
   - token is not expired;
   - token is not consumed.
3. If `return_to` is provided, validate against the server-configured allowlist.
4. Consume the intent (mark consumed, prevent reuse).
5. Create the login transaction with server-controlled values only.

If any validation fails, login fails closed. No login transaction is created.

### 2.8 What the browser is allowed to send

| Browser may send | Browser must NOT send |
|---|---|
| `intent_token` (required) | `role`, `roles`, `group`, `groups` |
| `return_to` (optional, validated) | `tenant`, `organization` |
| `Origin` header (required) | `environment` |
| `Referer` header (fallback) | `principal`, `subject`, `user` |
| | `token`, `access_token`, `id_token` |
| | Any field not explicitly listed |

### 2.9 TTL and expiry

The login intent has a short-lived, bounded lifetime that does not exceed the login transaction
lifetime.

- Intent creation sets an expiry timestamp.
- Expired intents are rejected at `POST /v1/auth/login`.
- Expired intents are eligible for server-side cleanup.
- The intent does not outlive its bounded lifetime under any circumstance.

### 2.10 Replay protection

- The intent is single-use: once consumed at `POST /v1/auth/login`, it cannot be reused.
- Duplicate submission of a consumed intent fails closed.
- The intent token is not predictable and cannot be forged.

### 2.11 Relationship to browser binding

The login intent and browser binding are complementary:

- **Browser binding** proves the callback originated from the same browser that initiated
  login (ADR-PORTAL-002-09).
- **Login intent** proves the login request was initiated by the Portal and binds the
  return path.

Both are validated at their respective steps. Neither is sufficient alone.

### 2.12 Relationship to OIDC state and PKCE

- **Login intent** is validated at `POST /v1/auth/login` (before OIDC redirect).
- **OIDC state** is validated at `GET /v1/auth/callback` (after OIDC redirect).
- **PKCE** is validated at `GET /v1/auth/callback` (during token exchange).

They protect different phases of the login flow and are independent mechanisms.

### 2.13 Relationship to login transaction

The login intent is consumed before the login transaction is created. The intent provides:

- CSRF validation for the login initiation;
- return-path binding.

The login transaction provides:

- OIDC state, nonce, PKCE verifier;
- browser-binding hash;
- provider binding.

The intent does not carry over to the login transaction. It is a pre-transaction validation
step.

### 2.14 Audit requirements

| Event | Audit data |
|---|---|
| Intent created | timestamp, selected_provider |
| Intent validated | timestamp, return_to (if any) |
| Intent missing | timestamp, failure_reason=missing |
| Intent expired | timestamp, failure_reason=expired |
| Intent consumed | timestamp |
| Intent replayed | timestamp, failure_reason=consumed |
| Forbidden field submitted | timestamp, failure_reason=forbidden_field |

The intent token itself never appears in audit events.

### 2.15 Failure behaviour

| Failure | Response | Transaction state |
|---|---|---|
| Intent missing | Fail closed — no login transaction | No transaction |
| Intent expired | Fail closed — no login transaction | No transaction |
| Intent consumed (replay) | Fail closed — no login transaction | No transaction |
| Invalid return_to | Fail closed — no login transaction | No transaction |
| Forbidden field submitted | Fail closed — no login transaction | No transaction |
| Origin mismatch | Fail closed — no login transaction | No transaction |

In all cases: no login transaction is created, no OIDC redirect occurs.

### 2.16 New governance decisions introduced

This amendment introduces the following new governance decisions:

- **Login-intent response schema** (login-context view fields) — the frozen design did not
  define the response shape.
- **Login-intent request contract** (what browser may/may not submit) — the frozen design
  did not specify browser-submitted fields.
- **Server-side intent storage model** — the frozen design did not define intent storage.
- **Forbidden browser-submitted fields** — the frozen design did not enumerate fields the
  browser must not send.
- **Intent validation procedure** — the frozen design did not define the validation order.

These are new governance decisions, not clarifications of existing frozen behavior.

### 2.17 What is OUT OF SCOPE

This amendment does NOT address:

- callback sequencing model (Blocker 6, Action 5);
- session creation or audit evidence in callback;
- OIDC state, nonce, or PKCE mechanisms;
- browser-binding mechanism (frozen in ADR-PORTAL-002-09);
- specific Python or FastAPI implementation code;
- database migration scripts;
- CI pipeline changes.

### 2.18 Consequences

- Login-context response schema is now defined.
- `POST /v1/auth/login` request contract is now defined.
- Forbidden browser-submitted fields are enumerated.
- Server-side intent storage requirements are defined.
- No frozen contracts are modified by this amendment.
- No runtime implementation is authorized by this document.

## 3. Status

**PROPOSED**

This amendment is a governance document. It does not authorize runtime implementation.

**Runtime implementation remains NOT AUTHORIZED by this amendment.**
